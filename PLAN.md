# Plan de correccion

## API

### H-API-01 — Token Base64 con secreto embebido y sin firma

- **Hallazgo en HALLAZGOS.md:** H-API-01, componente `api`, severidad alta, estado `Pendiente`. Evidencia registrada: `api/app/main.py:14`, `api/app/main.py:17`, `api/app/main.py:22`.
- **Problema:** `legacy_identity` decodifica un valor Base64 controlable por el cliente y compara sus campos con un secreto fijo en el codigo. No hay integridad criptografica ni validacion de emisor o audiencia; una fecha de expiracion no autentica por si sola las claims. Todas las rutas protegidas dependen de esta funcion.
- **Contrato/comportamiento a preservar:** no existe `docs/ENDPOINTS.md`. Tomar como referencia el contrato observado en `HALLAZGOS.md`: conservar las rutas, el esquema `Authorization: Bearer`, la respuesta `401` para credenciales invalidas y la identidad interna con `username` y `role`. Las respuestas de negocio de las rutas no deben cambiar por esta correccion. El formato interno Base64 actual no puede conservarse y, a la vez, obtener verificacion JWT real; no aceptar tokens legacy como alternativa, pues mantendria el hallazgo.
- **Cambio propuesto:** despues de confirmar el contrato del emisor, verificar JWT con una biblioteca mantenida en lugar de implementar criptografia propia. Validar firma usando un algoritmo fijado por el servidor, y validar `iss`, `aud` y `exp`; rechazar claims ausentes, expiradas o invalidas con `401` generico. Mapear las claims acordadas a `username` y `role` para que las rutas consumidoras mantengan su identidad actual. Obtener clave y valores de issuer/audience desde configuracion externa, sin secretos por defecto ni secretos reales en pruebas. Extraer la verificacion a una funcion/dependencia de seguridad con una responsabilidad; evitar parseo duplicado, anidamiento profundo y valores magicos.
- **Dependencia:** considerar `PyJWT` como dependencia de produccion porque la biblioteca estandar no valida JWT y no se debe implementar firma criptografica manualmente. Antes de fijar version, revisar advisories y compatibilidad con Python 3.13; registrar el resultado y justificar la version en `api/requirements.txt`. No se requiere dependencia de desarrollo adicional.
- **Archivos previstos:** `api/tests/test_api.py` (caracterizacion primero y casos JWT), `api/app/security.py` (nuevo modulo para validacion y mapeo de identidad), `api/app/main.py` (conectar la dependencia verificada a las rutas sin cambiar sus paths ni respuestas) y `api/requirements.txt` (solo tras revisar la dependencia). No tocar archivos de otros componentes.
- **Caracterizacion antes de tocar implementacion/configuracion:** en `api/tests/test_api.py`, ampliar los casos de autenticacion antes de cambiar `main.py` o dependencias. Fijar la linea base actual: un Bearer legacy vigente permite `GET /api/tasks` y mantiene las tareas/forma de respuesta actuales; token malformado, secreto incorrecto y token expirado reciben `401`. Ejecutar y registrar esa linea base antes del cambio. El test de aceptacion del token legacy documenta el comportamiento previo, pero se debe sustituir por pruebas de JWT en el mismo cambio de migracion, no dejarlo como bypass aceptado.
- **Pruebas posteriores previstas:** generar tokens firmados solo con una clave aislada de prueba; comprobar que un JWT valido conserva la identidad y el comportamiento HTTP de las rutas protegidas, y que firma incorrecta, `iss` incorrecto, `aud` incorrecta, `exp` vencida, claims requeridas ausentes, token malformado y ausencia de Bearer se rechazan con `401`. Ejecutar toda la suite desde `api/` con `python -m pytest`; registrar ejecucion y resultado en `docs/TESTING.md` cuando corresponda. Ninguna prueba se ha ejecutado como parte de este plan.
- **Pendientes/bloqueos:** confirmar con el responsable del emisor JWT el algoritmo, issuer, audience, nombres de claims para usuario/rol, formato Bearer, origen/rotacion de claves y disponibilidad de un token de integracion ficticio. Hasta tener esa evidencia no se puede afirmar compatibilidad extremo a extremo ni aprobar el cambio de formato; no se registra aprobacion humana. La propuesta mantiene la interfaz HTTP observada, pero la migracion del contenido del token requiere coordinacion antes de implementarse.

### H-API-02 — Autorizacion de tareas controlada por `owner` del cliente

- **Hallazgo en HALLAZGOS.md:** H-API-02, componente `api`, severidad alta, estado `Pendiente`. Evidencia registrada: `api/app/main.py:68`, `api/app/main.py:69`, `api/app/main.py:78`, `api/app/main.py:83`, `api/app/main.py:91`, `api/app/main.py:92`.
- **Problema:** `list_tasks` y `summary` prefieren el query `owner` a la identidad autenticada; `create_task` tambien permite definir el propietario en el cuerpo. Un cliente puede leer o crear tareas asociadas a otra identidad.
- **Contrato/comportamiento a preservar:** conservar `GET /api/tasks`, `GET /api/summary`, `POST /api/tasks`, sus esquemas de respuesta y los parametros/campos observados cuando se usan para la propia identidad. `docs/ENDPOINTS.md` no existe, asi que esto se basa en el comportamiento observado de `HALLAZGOS.md`. La lectura y creacion para identidades arbitrarias es el comportamiento vulnerable que debe dejar de aceptarse; si existe un flujo administrativo legitimo, requiere contrato y autorizacion por rol acordados antes de implementarlo.
- **Cambio propuesto:** derivar siempre el propietario efectivo de `identity["username"]` verificado. Mantener el query `owner` y el campo `owner` por compatibilidad de forma, pero rechazar con respuesta generica `403` los valores que no coincidan con la identidad; nunca usarlos para seleccionar/escribir datos. Aplicar una sola regla reutilizable de autorizacion, sin duplicarla entre endpoints. Este control depende de la identidad JWT verificada de H-API-01.
- **Archivos previstos:** `api/tests/test_api.py` (caracterizacion y regresiones), `api/app/main.py` (dependencias de identidad y rutas; o el modulo de rutas definido al abordar H-API-07). No tocar otros componentes.
- **Caracterizacion antes de tocar implementacion:** agregar pruebas que registren el comportamiento actual: consultar `/api/tasks?owner=trainer` selecciona tareas de `trainer`, `/api/summary?owner=trainer` resume ese propietario y el POST conserva un `owner` enviado. Registrar que estas pruebas demuestran la conducta vulnerable y reemplazar sus expectativas en el mismo cambio aprobado; no conservarlas como autorizacion valida. Agregar tambien casos base de lectura y creacion para `student`, que deben seguir funcionando.
- **Pruebas posteriores previstas:** comprobar que sin `owner` y con el propio `owner` se conserva respuesta y contenido; un `owner` distinto recibe `403` en ambas lecturas y en creacion; omitir `owner` al crear asigna la identidad verificada. Cubrir roles solo cuando exista una regla acordada; no inferir permisos administrativos. Ejecutar `python -m pytest` desde `api/` y registrar resultado real en `docs/TESTING.md` cuando corresponda.
- **Pendientes/bloqueos:** confirmar si existe un flujo de lectura/escritura entre propietarios y quien define roles administrativos. Hasta esa confirmacion, el plan no concede excepciones por rol.

### H-API-03 — Consultas SQLite construidas por concatenacion

- **Hallazgo en HALLAZGOS.md:** H-API-03, componente `api`, severidad alta, estado `Pendiente`. Evidencia registrada: `api/app/main.py:70`, `api/app/main.py:84`, `api/app/main.py:93`.
- **Problema:** filtros de tareas/resumen e inserciones incorporan valores recibidos concatenando texto SQL. Esto permite alterar la interpretacion de consultas y hace que texto ordinario con comillas pueda causar fallos.
- **Contrato/comportamiento a preservar:** conservar las rutas, filtros propios permitidos, orden de tareas, campos y formas JSON observadas. No modificar el esquema ni la semantica de filtros como parte de esta correccion; el control de propietarios se resuelve en H-API-02.
- **Cambio propuesto:** sustituir toda interpolacion/concatenacion SQL de valores por placeholders `?` y parametros de `sqlite3`, incluidos filtros, inserciones y lectura del registro creado. Mantener SQL estructural estatico y no duplicar construccion de consultas. La parametrizacion no sustituye la autorizacion por identidad.
- **Archivos previstos:** `api/tests/test_api.py` (regresiones), `api/app/main.py` (o repositorio SQLite separado al implementar H-API-07). No requiere dependencia nueva ni cambios de esquema.
- **Caracterizacion antes de tocar implementacion:** agregar primero pruebas de linea base para listar, filtrar por el propio propietario, crear una tarea y calcular el resumen, comprobando los mismos campos/valores y codigos actuales. Agregar una prueba de texto ordinario con apostrofe en el titulo o descripcion como regresion esperada; registrar que falla en la implementacion actual antes de corregir SQL, sin usar payloads de explotacion.
- **Pruebas posteriores previstas:** la tarea con apostrofe se crea y se devuelve literalmente, las consultas mantienen aislamiento por propietario y datos entrecomillados no alteran resultados ajenos; repetir las pruebas de lista, alta y resumen. Ejecutar `python -m pytest` desde `api/`.

### H-API-04 — Carga de archivos usa directamente `file.filename`

- **Hallazgo en HALLAZGOS.md:** H-API-04, componente `api`, severidad alta, estado `Pendiente`. Evidencia registrada: `api/app/main.py:108`, `api/app/main.py:109`, `api/app/main.py:110`.
- **Problema:** el nombre controlado por el cliente se concatena con el directorio de uploads y el contenido completo se lee sin limite. No se normaliza el nombre ni se valida extension o tamano antes de escribir.
- **Contrato/comportamiento a preservar:** conservar `POST /api/requirements`, multipart con el campo `file`, `201` y la forma de respuesta (`owner`, `fileName`, `storedAt`, `size`) para archivos validos. La aceptacion sin limite de tipos/tamano ni el uso de nombres sin normalizar no se consideran garantias que deban preservarse.
- **Cambio propuesto:** validar que el nombre exista, normalizarlo a un nombre base seguro, comprobar extension contra una allowlist acordada y limitar bytes leidos mediante configuracion con nombre (sin numero magico). Guardar el contenido de forma acotada; rechazar archivos invalidos con error HTTP generico y limpiar cualquier archivo parcial. No confiar en MIME enviado por cliente como unica validacion.
- **Archivos previstos:** `api/tests/test_api.py` (casos de carga), `api/app/main.py` o un servicio de carga bajo `api/app/` al organizar capas en H-API-07, y configuracion de `api/` solo si el limite/allowlist se externalizan. No cambiar otros componentes.
- **Caracterizacion antes de tocar implementacion:** ampliar primero `test_uploads_requirement` para fijar el caso valido existente (`requirements.txt`, `text/plain`), status `201`, campos de respuesta y contenido guardado. Anadir casos de nombre/extensiones y contenido por encima del futuro limite como regresiones pendientes de la politica; marcar como no ejecutables contra la implementacion actual si aun no existe limite.
- **Pruebas posteriores previstas:** un `.txt` valido dentro del limite conserva status, respuesta y bytes; extension no permitida y archivo que supera el limite se rechazan con `4xx`, sin crear archivos fuera del directorio destino ni dejar archivos parciales. Probar limites justo por debajo, en y por encima del maximo configurado. Ejecutar `python -m pytest` desde `api/`.
- **Pendientes/bloqueos:** acordar allowlist de extensiones, tamano maximo, codigo de error y nombres duplicados. No fijar valores arbitrarios ni suponer que solo se aceptan requisitos `.txt` por la unica prueba actual.

### H-API-05 — Manejo de errores amplio y contratos poco tipados

- **Hallazgo en HALLAZGOS.md:** H-API-05, componente `api`, severidad media, estado `Pendiente`. Evidencia registrada: `api/app/main.py:25`, `api/app/main.py:78`, `api/app/main.py:94`, `api/app/main.py:101`, `api/app/main.py:120`, `api/app/main.py:121`.
- **Problema:** excepciones generales convierten detalles internos en respuestas; requests y responses se expresan como `dict[str, Any]`; la agregacion de resumen usa estado mutable y condicionales anidados. Esto puede exponer informacion, aceptar formas inesperadas y complicar cambios seguros.
- **Contrato/comportamiento a preservar:** mantener nombres de campos, defaults actualmente observables, codigos de exito y estructuras JSON de tareas, resumen, carga y health. Para errores, mantener los codigos HTTP documentados/observados pero reemplazar detalles internos por mensajes genericos. No endurecer validaciones de negocio no acordadas.
- **Cambio propuesto:** definir modelos Pydantic de entrada/salida que representen los campos y defaults existentes, y usarlos como tipos de FastAPI. Traducir errores esperados a `HTTPException` con detalle generico; limitar capturas a excepciones esperadas y dejar registro controlado del detalle en servidor, nunca en la respuesta. Simplificar el conteo del resumen con una pasada clara y condiciones combinadas o funciones pequenas; evitar duplicacion y estado innecesario. Coordinar el error generico de token con H-API-01.
- **Archivos previstos:** `api/tests/test_api.py` (contratos y errores), `api/app/schemas.py` (modelos Pydantic nuevos), `api/app/main.py` (tipos, errores y reglas; o rutas/servicios separados en H-API-07). No añadir libreria: Pydantic ya esta fijado en `api/requirements.txt`.
- **Caracterizacion antes de tocar implementacion:** agregar pruebas que congelen las respuestas actuales de tareas, creacion, resumen, carga y health (usando un sustituto local para no depender de auth externo), incluidos defaults de campos omitidos. Registrar la respuesta de error actual de token invalido como evidencia previa, pero reemplazar la expectativa de detalle crudo por mensaje generico en la correccion; no hacer depender una prueba de la cadena interna de una excepcion.
- **Pruebas posteriores previstas:** verificar respuestas validas contra los modelos y mantener exactamente las claves JSON/codigos observados; comprobar que errores de autenticacion y fallos esperados de health no exponen texto de excepcion; validar rechazos de request solo para tipos incompatibles con el esquema acordado. Cubrir resumen vacio, estados repetidos y estados no terminales. Ejecutar `python -m pytest` desde `api/`.
- **Pendientes/bloqueos:** acordar si el campo `owner` recibido en el body permanece como campo de compatibilidad mientras H-API-02 lo rechaza cuando no coincide; revisar los modelos contra consumidores antes de endurecer validacion. Las rutas de health actualmente devuelven detalles de error y requeriran un ajuste deliberado de respuesta.

### H-API-06 — Dependencias fijadas requieren verificacion SCA

- **Hallazgo en HALLAZGOS.md:** H-API-06, componente `api`, severidad baja, estado `Pendiente`. Evidencia registrada: `api/requirements.txt:4`, `api/requirements.txt:5`.
- **Problema:** el manifiesto fija `urllib3==2.5.0` y `python-multipart==0.0.21`, versiones que el reto solicita investigar. La fijacion por si sola no confirma ni descarta advisories aplicables.
- **Contrato/comportamiento a preservar:** `urllib3` se usa para consultar health del backend y `python-multipart` soporta el endpoint multipart. Mantener esas capacidades y compatibilidad con Python 3.13; no retirar una dependencia que siga siendo necesaria.
- **Cambio propuesto:** obtener un inventario y reporte SCA reproducibles para versiones directas y transitivas, verificar CVEs/advisories contra fuentes actuales y determinar versiones corregidas compatibles. Actualizar solo los pines con evidencia; si una dependencia deja de ser necesaria tras cambios aprobados, evaluar su remocion con pruebas que demuestren que la funcionalidad permanece. No silenciar alertas ni reducir quality gates.
- **Archivos previstos:** `api/requirements.txt` solo si el analisis confirma actualizacion o remocion necesaria; `api/tests/test_api.py` unicamente si la actualizacion causa cambios funcionales que requieren regresion. No introducir herramientas de escaneo como dependencia de produccion; coordinar el scanner aprobado externamente si no esta disponible en el entorno.
- **Caracterizacion antes de tocar dependencias:** guardar version de Python, inventario resuelto y reporte SCA previo para las dependencias de `api/requirements.txt`; comprobar tambien que la suite actual pasa antes del cambio. Este reporte es la linea base del hallazgo, no se afirma aqui que una version tenga un CVE concreto.
- **Pruebas posteriores previstas:** repetir el mismo analisis SCA tras el cambio, revisar diferencias de advisories y resolver todas las alertas aplicables sin exclusiones; ejecutar `python -m pytest` desde `api/` y verificar que health y carga multipart conservan sus respuestas. Registrar comandos, versiones y resultados reales en `docs/TESTING.md` cuando corresponda.
- **Pendientes/bloqueos:** no se ha consultado ni ejecutado un scanner en este paso. Requiere evidencia actual del scanner/fuentes, compatibilidad de versiones y disponibilidad del servicio de revision de dependencias; no registrar CVE, remocion ni actualizacion como hecho hasta obtenerla.

### H-API-07 — Rutas, persistencia, reglas y serializacion concentradas en un modulo

- **Hallazgo en HALLAZGOS.md:** H-API-07, componente `api`, severidad baja, estado `Pendiente`. Evidencia registrada: `api/app/main.py:29`, `api/app/main.py:37`, `api/app/main.py:56`, `api/app/main.py:67`, `api/app/main.py:77`, `api/app/main.py:90`.
- **Problema:** `main.py` crea esquema/seed SQLite, contiene serializacion y define rutas que consultan datos y aplican reglas. El acoplamiento mezcla transporte, persistencia y negocio, haciendo mas costoso aislarlos y probarlos.
- **Contrato/comportamiento a preservar:** como no existe `docs/ENDPOINTS.md`, usar las cinco rutas y respuestas observadas en `HALLAZGOS.md` como linea base. Mantener paths, metodos, codigos de exito y claves JSON; aplicar los cambios de seguridad de H-API-02 y H-API-04 solo en sus comportamientos vulnerables documentados. Preservar inicializacion/seed de SQLite y configuracion `create_app` usada por las pruebas.
- **Cambio propuesto:** separar rutas FastAPI, reglas de servicio y acceso SQLite en modulos con responsabilidad unica (por ejemplo `api/app/routes.py`, `api/app/services.py`, `api/app/repositories.py`); mantener `create_app` como composition root que configura dependencias, middleware, rutas y cierre de conexion. Reutilizar modelos de `api/app/schemas.py` de H-API-05 y el validador de `api/app/security.py` de H-API-01, en vez de duplicarlos. Mantener las consultas parametrizadas de H-API-03 dentro del repositorio y las reglas de identidad de H-API-02 en una sola capa.
- **Archivos previstos:** `api/tests/test_api.py` (caracterizacion/regresion), `api/app/main.py`, y los modulos nuevos `api/app/routes.py`, `api/app/services.py`, `api/app/repositories.py`; integrar sin reescribir los cambios de los hallazgos previos. No requiere dependencias nuevas.
- **Caracterizacion antes de tocar arquitectura:** completar primero pruebas de contrato para las cinco rutas: autenticacion, metodos/paths, status, claves y tipos de respuesta; cubrir listado y creacion de tareas, resumen, carga valida y health con dependencia externa simulada. Fijar `create_app` con base y uploads temporales para aislar persistencia. Ejecutar y registrar la suite antes de mover funciones.
- **Pruebas posteriores previstas:** correr las mismas pruebas de caracterizacion contra la nueva estructura y verificar que crear dos aplicaciones con almacenes temporales distintos no comparte datos/conexiones. Ejecutar toda la suite `python -m pytest` desde `api/`; revisar cobertura de codigo modificado con el gate existente, sin cambiar umbrales, y registrar resultado real en `docs/TESTING.md`.
- **Pendientes/bloqueos:** implementar despues de caracterizar y revisar H-API-01 a H-API-06 para evitar resolver varias causas en un movimiento opaco. La cobertura objetivo y la revision humana aplican segun `AGENTS.md`; no se asume aprobacion ni resultado de pruebas.
