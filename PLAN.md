# Plan de correccion

## API

### H-API-01 — Token Base64 con secreto embebido y sin firma

- **Hallazgo en HALLAZGOS.md:** H-API-01, componente `api`, severidad alta, estado `Pendiente`. Evidencia registrada: `api/app/main.py:14`, `api/app/main.py:17`, `api/app/main.py:22`.
- **Problema:** `legacy_identity` decodifica un valor Base64 controlable por el cliente y compara sus campos con un secreto fijo en el codigo. No hay integridad criptografica ni validacion de emisor o audiencia; una fecha de expiracion no autentica por si sola las claims. Todas las rutas protegidas dependen de esta funcion.
- **Contrato/comportamiento a preservar:** no existe `docs/ENDPOINTS.md`. Tomar como referencia el contrato observado en `HALLAZGOS.md`: conservar las rutas, el esquema `Authorization: Bearer`, la respuesta `401` para credenciales invalidas y la identidad interna con `username` y `role`. Las respuestas de negocio de las rutas no deben cambiar por esta correccion. El formato interno Base64 actual no puede conservarse y, a la vez, obtener verificacion JWT real; no aceptar tokens legacy como alternativa, pues mantendria el hallazgo.
- **Cambio propuesto:** despues de confirmar el contrato del emisor, verificar JWT con una biblioteca mantenida en lugar de implementar criptografia propia. Validar firma usando un algoritmo fijado por el servidor, y validar `iss`, `aud` y `exp`; rechazar claims ausentes, expiradas o invalidas con `401` generico. Mapear las claims acordadas a `username` y `role` para que las rutas consumidoras mantengan su identidad actual. Obtener clave y valores de issuer/audience desde configuracion externa, sin secretos por defecto ni secretos reales en pruebas. Extraer la verificacion a una funcion/dependencia de seguridad con una responsabilidad; evitar parseo duplicado, anidamiento profundo y valores magicos.
- **Dependencia:** considerar `PyJWT` como dependencia de produccion porque la biblioteca estandar no valida JWT y no se debe implementar firma criptografica manualmente. Antes de fijar version, revisar advisories y compatibilidad con Python 3.13; registrar el resultado y justificar la version en `api/requirements.txt`. No se requiere dependencia de desarrollo adicional.
- **Archivos previstos:** `api/tests/test_api.py` (caracterizacion primero y casos JWT), `api/app/security.py` (nuevo modulo para validacion y mapeo de identidad), `api/app/main.py` (conectar la dependencia verificada a las rutas sin cambiar sus paths ni respuestas) y `api/requirements.txt` (solo tras revisar la dependencia). No tocar archivos de otros componentes.
- **Caracterizacion antes de tocar implementacion/configuracion:** en `api/tests/test_api.py`, ampliar los casos de autenticacion antes de cambiar `main.py` o dependencias. Fijar la linea base actual: un Bearer legacy vigente permite `GET /api/tasks` y mantiene las tareas/forma de respuesta actuales; token malformado, secreto incorrecto y token expirado reciben `401`. Ejecutar y registrar esa linea base antes del cambio. El test de aceptacion del token legacy documenta el comportamiento previo, pero se debe sustituir por pruebas de JWT en el mismo cambio de migracion, no dejarlo como bypass aceptado.
- **Pruebas posteriores previstas:** generar tokens firmados solo con una clave aislada de prueba; comprobar que un JWT valido conserva la identidad y el comportamiento HTTP de las rutas protegidas, y que firma incorrecta, `iss` incorrecto, `aud` incorrecta, `exp` vencida, claims requeridas ausentes, token malformado y ausencia de Bearer se rechazan con `401`. Ejecutar toda la suite desde `api/` con `python -m pytest`; registrar ejecucion y resultado en `docs/TESTING.md` cuando corresponda. Ninguna prueba se ha ejecutado como parte de este plan.
- **Pendientes/bloqueos:** confirmar con el responsable del emisor JWT el algoritmo, issuer, audience, nombres de claims para usuario/rol, formato Bearer, origen/rotacion de claves y disponibilidad de un token de integracion ficticio. Hasta tener esa evidencia no se puede afirmar compatibilidad extremo a extremo ni aprobar el cambio de formato; no se registra aprobacion humana. La propuesta mantiene la interfaz HTTP observada, pero la migracion del contenido del token requiere coordinacion antes de implementarse.
