# Validación de firma del token de autenticación

## Fuente

- **Hallazgo:** H-AUTH-03 — Token Base64 con secreto embebido y sin firma. Estado: `Pendiente`; el emisor ya genera JWT firmado, pero falta verificar la validación en los consumidores.
- **Evidencia:** [HALLAZGOS.md](./HALLAZGOS.md), matriz de seguimiento y contrato observado; `auth/src/main/java/com/bcp/workshop/auth/AuthResource.java:51`; `auth/src/main/java/com/bcp/workshop/auth/TokenSigner.java:18-75`. El hallazgo registra que no se encontró un flujo de validación dentro de `auth/` y que no se inspeccionaron los consumidores fuera de ese componente.
- **Impacto:** si un consumidor acepta claims sin verificar la firma, un token alterado o no emitido por el servicio podría ser tratado como autenticado o autorizado. La evidencia disponible no confirma que esto ocurra: los consumidores aún no fueron inspeccionados.

## Contexto actual

El emisor de `auth` crea un JWT compacto firmado con HS256 e incluye los claims `sub`, `role` y `exp`. La verificación de la firma por los consumidores no está demostrada. No se cuenta todavía con un inventario confirmado de esos consumidores ni con evidencia de sus rutas de autenticación y autorización.

## Problema confirmado

No hay evidencia suficiente para asegurar que cada consumidor valida la firma del token antes de confiar en sus claims. Por tanto, sigue sin poder confirmarse que los consumidores distingan un token válido emitido por `auth` de uno con firma inválida o contenido alterado.

## Comportamiento a preservar

- Mantener `POST /auth/login`, sus campos de solicitud y sus respuestas observadas: `400` para solicitud o campos requeridos inválidos, `401` para credenciales no válidas y `200` con `token`, `expiresIn`, `user` (`username`, `displayName`, `role`) y `debug` para autenticación exitosa.
- Mantener el formato JWT HS256 y los claims `sub`, `role` y `exp` emitidos por `auth`.
- No cambiar implícitamente los contratos de las operaciones consumidoras ni definir para ellas códigos o cuerpos de error que no estén documentados.

## Alcance

- Identificar los consumidores reales de los tokens emitidos por `auth` y los puntos donde usan el token para autenticación o autorización.
- Verificar que cada consumidor valide la firma antes de confiar en los claims.
- Comprobar para cada consumidor que acepta un token válido emitido por `auth` y rechaza un token con firma inválida o con contenido alterado.
- Registrar los consumidores revisados y la evidencia de las comprobaciones.

## Fuera de alcance

- Cambiar la ruta, los campos, los códigos de respuesta o el formato de `POST /auth/login`.
- Cambiar el formato, algoritmo o claims del token emitido por `auth`.
- Definir o modificar contratos de respuesta para el rechazo de tokens en los consumidores.
- Abordar otros hallazgos o candidatos no incluidos en H-AUTH-03.

## Criterios de aceptación

1. Existe un inventario de los consumidores reales revisados, con componente y punto de uso del token identificados.
2. Para cada consumidor identificado, una prueba demuestra que acepta un token válido emitido por `auth`.
3. Para cada consumidor identificado, una prueba demuestra que rechaza un token con firma inválida y no lo trata como autenticado ni autorizado.
4. Para cada consumidor identificado, una prueba demuestra que rechaza un token cuyo contenido fue alterado sin una firma válida.
5. Las pruebas y su ejecución registran los comandos utilizados y el número de casos aprobados y fallidos.
6. La verificación no modifica el contrato observado de `POST /auth/login` ni el formato del token emitido.

## Contratos afectados/protegidos

- **Protegido — `POST /auth/login`:** ruta, campos de solicitud, códigos de respuesta y forma JSON enumerados en «Comportamiento a preservar».
- **Protegido — token de `auth`:** JWT HS256 con claims `sub`, `role` y `exp`.
- **Afectado — consumidores:** autenticación y autorización basadas en tokens emitidos por `auth`. Los endpoints, las respuestas de rechazo y cualquier contrato consumidor adicional no están documentados en la evidencia disponible; no se les asignarán cambios implícitos.

## Riesgos, supuestos y preguntas abiertas

- El inventario de consumidores no está confirmado; la validación puede requerir ampliar el alcance a componentes distintos de `auth`.
- No está documentado cómo obtiene cada consumidor el material de verificación ni qué política aplica al algoritmo. Debe confirmarse durante la revisión de cada consumidor, sin asumir una configuración.
- Los contratos actuales de error para tokens inválidos en consumidores no se conocen; se preservarán y no se fijará un estado HTTP o cuerpo nuevo en esta spec.
- El impacto de aceptar tokens alterados es condicional: la evidencia disponible no prueba que algún consumidor omita la verificación.
- Esta spec queda sujeta a revisión humana antes de ampliar el alcance o iniciar su implementación.
